## 1. Settled decisions (summary)

- **D1. Week 1 only.** The athlete fills week 1 prescriptions only. Weeks 2+ are generated by the progression engine. *Decided.*
- **D2. Projection.** Before any performance exists, weeks 2+ are projected at **+1 equipment step per week**, using the existing equipment step table, plus the existing RPE ramp (7 → 10). The UI labels projections as a *preview*, not a promise. *Decided.*
- **D3. Adjustment.** After each completed session, the engine regenerates **all future weeks** for the exercises performed, **except prescriptions the athlete edited manually**. A manually edited week becomes the anchor that later weeks project from. *Decided.*
- **D4. Pyramids.** Every working set steps by the same increment. Implement this as a plain function parameter, not a strategy pattern. Other increment strategies may come later. *Decided.*
- **D5. Strength test.** New final-week strategy `strength_test`. Details are in item G1. *Decided in principle; some details Proposed.*
- **D6. Carryover.** Strength test results feed the next mesocycle's week 1 through an explicit action. Details are in item G2. *Decided in principle; details Proposed.*
- **D7. Restart.** Restart = stop (keep as abandoned history) + copy including prescriptions + start the copy. Performed sessions are **never deleted** by a restart. *Decided.*
- **D8. Draft order.** Draft order is purely visual. The **first draft in order is "next"**; there is no separate "next" flag. *Decided.*
- **D9. "Week" terminology.** Keep the term "Week". Weeks are session-based, not calendar-based. The UI shows "Week N · Day X of Y" and never shows dates. *Decided.*
- **D10. Coarse muscles.** Use coarse muscles now, keep the numeric contribution weights, and add a nullable `parent_muscle_id` so granularity can be added later as rows rather than a migration. **This changes [`constitution.md`](../constitution.md) §3 ("Muscles are granular"); update it explicitly.** *Decided.*
- **D11. Prescription fields.** Set type, tempo and rep range belong to the set prescription only, never to the Exercise. *Decided.*

## 2. Items

Original point numbers from the author's raw list are given as (#n).

### A. Bugs

**A1. Workout page prefills the wrong weight for sets 2+ (#14).** ☐
- **Observed:** An exercise was prescribed 3 sets: 20 kg × 10, 40 kg × 6, 50 kg × 4. On the workout page, set 1 prefilled correctly. Sets 2 and 3 prefilled with the previous set's weight instead of their own prescribed weight.
- **Expected:** Each set prefills with its own prescribed target weight. Reps and RPE stay blank, as already decided.
- **Suspected cause:** Somewhere the code assumes one weight per exercise rather than one per set, either in the prefill logic or in how recommendations are stored. Check whether the progression engine shares this assumption.
- **Acceptance:** A pyramid prescription prefills every set correctly. A test covers this.

**A2. Progression engine doesn't produce future-week targets (#15).** ☐
- **Observed:** The author filled every week's prescriptions manually. After completing sessions, future weeks were not adjusted, and adjusted targets didn't appear on the workout page.
- **Suspected cause:** Per the brief, the engine skips generation when a prescription already exists for that slot and week. Manually filling every week therefore disabled the engine. **Confirm this in code before relying on it.**
- **Resolution:** The redesign in section F supersedes this. Confirm the root cause first anyway, so the redesign doesn't inherit the same flaw.

**A3. Exercise form exposes set types, tempos and rep range (#2, #3).** ☐
- **Observed:** Creating an exercise shows every set type and tempo as selectable, and shows a target rep range.
- **Expected:** None of these belong to the Exercise (D11). The brief already says rep range was removed from Exercise, so if it still appears anywhere, that is implementation drift. Locate it.
- **Acceptance:** Exercise create and edit screens, API schemas and the model contain no set type, tempo or rep range fields. Covered in B1.

### B. Exercise library simplification

**B1. Coarse muscles and a leaner Exercise (#1, #2, #3).** ☐
- Use the existing `muscle_group` taxonomy as the coarse muscle list: chest, back, shoulders, biceps, triceps, core, glutes, quadriceps, hamstrings, calves, tibialis, plus the full_body and other catch-alls.
- Keep the numeric contribution weights. Add a nullable `parent_muscle_id` to the muscle table.
- Remove `supported_set_types` and `supported_tempos` from Exercise (model, API and UI). Any set type or tempo can be prescribed for any exercise.
- Note: `warmup_set` in `supported_set_types` previously encoded "can be ramped into with warm-up sets". With it removed, warm-up sets can be prescribed for any exercise. Update the decisions log accordingly.
- **The migration must be non-destructive.** Real exercise, mesocycle and session data exists, so map existing granular muscle rows onto the coarse ones. See open question Q1.
- Update [`constitution.md`](../constitution.md) §3 as described in D10.

### C. Mesocycle creation and planning

**C1. Creation flow (#4, #7).** ☐
- **Step 1 form** asks for three things only:
  - name;
  - length in weeks (4–12);
  - final-week strategy (`rest` / `reduced_load` / `none` / `strength_test`).
- The form does **not** ask for training days.
- Label the strategy field **"Final week"**, not "Deload", because `strength_test` isn't a deload in the fatigue-dissipation sense.
- **Cancel** on step 1 returns Home and creates nothing.
- **Create** saves the draft and lands directly on the **Training days** tab.
- Every builder tab has a clear way back Home. The draft persists.

**C2. Reorder exercises within a training day (#8).** ☐
- The backend endpoint `PATCH .../order` already exists, so this is a UI task. Existing lock rules apply: reordering is not allowed after the mesocycle has started.
- *Proposed:* use up/down buttons rather than drag-and-drop. They are simpler to build and more reliable with sweaty thumbs. See Q6.

**C3. Prescriptions tab: week 1 only (#9).** ☐
- Only week 1 is required input.
- Weeks 2+ are shown as a projected preview generated by the engine (D2), visibly marked as projected.
- The athlete *may* override a future week. Doing so marks it manual (see F2).
- Saving or editing week 1 regenerates the projections immediately.
- *Proposed:* Starting a mesocycle is blocked, with a message listing what's missing, if any exercise slot has no week 1 prescription. See Q3.

**C4. Faster prescription entry (#10).** ☐
- Duplicate a set.
- "Add set" pre-fills from the previous set's values.
- Apply one value (rep range, set type or tempo) to all sets of an exercise.
- Claude Code may propose other speed-ups. The author explicitly asked for "any other improvement".

### D. Mesocycle lifecycle and navigation

**D-1. Draft list management (#5).** ☐
- From Home, drafts can be **deleted**, with confirmation, and **reordered**.
- The active mesocycle is always pinned first and cannot be reordered. This keeps the current behaviour, which the author wants preserved.
- The first draft in order shows a "Next" badge (D8).

**D-2. Mesocycle viewer (#11, #16).** ☐
- Home offers **View mesocycle** for the active mesocycle, in addition to Start/Continue Workout.
- The viewer shows the current position ("Week N · Day X of Y"), training days, exercises per day, and prescribed sets per week.
- Each prescription shows where it came from (athlete / projected / adjusted) and, for engine-generated ones, the reason text (F3).
- Future weeks can be edited from the viewer under the existing lock rules (no edits to a week with a completed session). Edits mark the prescription manual. A **"Reset to auto"** action returns it to engine control.
- *Out of scope:* performed-vs-prescribed history inside the viewer. That belongs to the History milestone.

**D-3. Stop / Restart / Drop with confirmation (#11).** ☐
- **Stop:** end now and keep the mesocycle as abandoned history. *Proposed definition.*
- **Drop:** permanently delete the mesocycle and its sessions. Use the strongest confirmation wording. *Proposed definition.*
- **Restart:** as defined in D7. Week 1 and manual edits are kept, and projections are regenerated. This needs a copy variant that includes prescriptions, since the existing copy duplicates shape only. Depends on section F.
- Every action shows a confirmation dialog that states the consequence in plain words before anything happens.
- Restart was declined on 2026-08-30. **This is an intentional reversal.** Log it as such in the decisions log.

**D-4. Week label everywhere (D9).** ☐
- Home and Workout show "Week N · Day X of Y".

### E. Workout page

**E1. Show the plan, and improve the layout (#12, #13, #15).** ☐
- Each exercise is shown as a card listing every prescribed set in order. Each row shows:
  - set number;
  - set type badge (warm-up, straight, drop, and so on);
  - tempo, if not normal;
  - target weight;
  - rep range;
  - target RPE.
- Prefill follows A1: weight from the set's own target, reps and RPE blank.
- **Warm-up sets have no RPE input** (#13). The API accepts null RPE for warm-up sets. Progression already ignores warm-ups.
- The exercise card shows a short, collapsible explanation of *why* the targets are what they are (F3). This is a constitution requirement.
- Keep the mobile-first constraints: dark theme, large touch targets, minimal typing, usable one-handed.
- Already-logged sets stay as a read-only summary. Editing logged sets is not in scope.

### F. Progression engine redesign

*Do a design pass first. Show the author the rule table and the test-case list before writing engine code.*

**F1. Projection (D1, D2).** ☐
- From week 1, each later normal week = previous week + 1 equipment step for every working set (D4), using the same rep range, set count, set type and tempo.
- Warm-up sets carry forward unchanged, as already decided.
- The target RPE ramp is unchanged.
- The final week is generated from the last normal week according to its strategy:
  - `reduced_load`: the existing 50% rule;
  - `rest`: nothing generated;
  - `none`: a normal week;
  - `strength_test`: see G1.
- Projection runs whenever week 1 (or an anchoring manual week) changes, including on drafts.

**F2. Adjustment after a session (D3).** ☐
- When a session completes, apply the **existing decision rule table** for each exercise performed. The table itself is unchanged:
  - missed the bottom of the rep range → −1 step;
  - hit the top of the range at ≤ target RPE + 1 → +1 step;
  - RPE ≥ target + 2 on every working set → −1 step;
  - otherwise → hold.
- That decision sets the **next** week. Every week after it is re-projected at +1 step per week from there, then the final week by strategy.
- **Skip manual prescriptions.** A manual week is never overwritten, and the weeks after it project from it.
- Remove the old "skip if a prescription exists" rule. It is replaced by this source-aware behaviour.
- Add a source field with the values `athlete` / `projected` / `adjusted`. *Proposed:* track the source at the **exercise prescription (slot + week)** level rather than per set. Editing any set of an exercise-week marks that whole exercise-week manual. Per-set tracking would let the engine rewrite sets 1 and 3 around a manually edited set 2, which is confusing. See Q4.
- Weeks with a completed session stay locked, as already decided.

**F3. Explanations.** ☐
- Every engine-generated prescription stores a plain-language reason. Examples:
  - "Projected: +1 step from week 2. Preview only; it updates after your sessions."
  - "Increased: you hit the top of the rep range at RPE 8 on all working sets."
- These reasons are shown on the workout page and in the viewer.

**F4. Tests.** ☐
Unit-test the engine without a database, covering at least:
- projection over 4, 8 and 12 weeks for each equipment type, including the dumbbell tier crossing 10 kg;
- a pyramid stepping uniformly;
- warm-ups carried forward unchanged;
- each rule-table branch;
- a manual week left untouched and used as the anchor;
- "Reset to auto";
- missed, skipped or partial sessions;
- an exercise swap;
- every final-week strategy.

### G. Final week strategy and block transitions

**G1. `strength_test` final week (#6, D5).** ☐
- Add `strength_test` as a new value in the existing deload/final-week strategy table. It replaces the last week, using the same placement logic as the other strategies.
- **Sets:** `ceil(working sets of the last normal week / 2)` per exercise. Warm-up sets are kept unchanged.
- **Reps:** same rep range as the previous weeks.
- **Weight:** last normal week + **1 step**. *Proposed:* the author was undecided between +1 and +2; +1 is recommended because +2 (often 10 kg on a barbell) mostly produces missed reps. Keep it a single named constant.
- **Target RPE: 10.** This is an explicit exception to the current rule that final weeks get no target RPE.
- *Proposed:* which sets to keep when halving a pyramid. Keep the **last** `ceil(n/2)` working sets, which are the heavy end. For straight sets the result is identical. See Q5.

**G2. Carryover to the next mesocycle (D6).** ☐
- Add an explicit **"Prefill week 1 from last block"** action on a draft's Prescriptions tab.
- **Source block:** the most recently **completed** mesocycle. *Proposed:* never an abandoned one.
- **Scope:** only exercises present in both blocks.
- **Prefill content:** the previous block's week 1 set structure (sets, reps, set type, tempo), with weights set as follows:
  - previous final week was `strength_test` and the athlete reached at least the bottom of the rep range on all working sets → previous week 1 + 1 step;
  - previous final week was `strength_test` and the athlete missed → previous week 1 unchanged;
  - previous final week was any other strategy → use the previous block's **week 2** weights (the author's original idea, kept as the fallback).
- *Proposed:* "hit" means reached at least the bottom of the rep range on all working sets. See Q5.
- *Proposed:* only fill empty exercise slots. Ask for confirmation before overwriting slots that are already filled.
- The reason text explains the carryover, e.g. "Your strength test confirmed progress: starting one step above last block's week 1."

**G3. Start the next draft (D8).** ☐
- When a mesocycle completes, Home offers "Start [next draft]?".
- Confirming starts it, subject to the normal start rules (C3).

## 3. Known open questions (ask the author)

- **Q1. Muscle migration.** How do granular contributions merge into a coarse muscle? For example, upper chest 1.0 + mid chest 0.5 → chest = max (1.0)? A sum capped at 1.0? Should any coarse muscles be added (forearms, adductors, abductors, traps)?
- **Q2. Adjustment base.** Does adjustment step from the weight actually **performed** in each set, or from the **prescribed** weight? State what the current engine does and propose one.
- **Q3. Starting with an incomplete week 1.** Block the start (proposed), or allow it with a warning?
- **Q4. Manual-edit granularity.** Per exercise-week (proposed) or per set?
- **Q5. Strength test details.** Which sets are kept when halving (proposed: the heavy end)? What counts as "hit" (proposed: bottom of the rep range on all working sets)? +1 or +2 steps?
- **Q6. Reordering UI.** Up/down buttons (proposed) or drag-and-drop?
- **Q7. Viewer scope.** Should the viewer also open completed and abandoned mesocycles, or only the active one for now?
