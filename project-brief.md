## 1. Context & Constraints (current)

- **Time budget:** Variable week to week — no fixed weekly hour commitment.
- **Timeline pressure:** Whoop subscription ends in ~100 days from 2026-08-25 (~early December 2026). Goal: a version usable for **daily training** before then. This favors shipping the core loop (auth → program → workout logging → basic recommendations → offline) over breadth.
- **Devices:** Android (author) + iOS (girlfriend), day one, both in the EU (Portugal). PWA install works normally on iOS in the EU (a 2024 Apple/DMA scare over this was reversed within two weeks and has stayed reversed) — but iOS still has no automatic "Add to Home Screen" prompt like Android does, and iOS Safari does not support the Background Sync API at all. See `architecture-discovery.md` §4 for the full offline-sync design this forces.

- **Frontend experience:** None (no JS/TypeScript, no Docker) prior to this project. Treat as fully greenfield; teach inline.

## 2. Technology Stack (decided 2026-08-25 — see `architecture-discovery.md` for full rationale)

- **Backend framework:** FastAPI (confirmed compatible with Python 3.14).
- **Package manager:** uv (not Poetry).
- **ORM / migrations:** SQLAlchemy 2.x + Alembic. Plain SQLAlchemy models for persistence and separate Pydantic models for the API — **deliberately not SQLModel**, since merging table + API schema into one class conflicts with the constitution's clean-architecture principle (domain logic must stay independent of persistence).
- **Password hashing:** argon2-cffi (Argon2id) — current OWASP recommendation, confirmed Python 3.14 support.
- **Database:** PostgreSQL.
- **Database hosting:** Neon (free tier) — scale-to-zero, no idle-pause, no card required.
- **Backend hosting:** Render (free tier) to start. Sleeps after 15 min idle with a 30-60s cold start on wake, but this doesn't affect workout logging itself since that's fully offline-first — only sync is delayed. Revisit Fly.io (~$2/month, always-on) later if cold starts prove annoying in practice.
- **Frontend framework:** React + TypeScript.
- **Offline storage:** Dexie.js (IndexedDB wrapper), with `dexie-react-hooks` for reactive UI updates.
- **Sync strategy:** Manual/triggered sync — queue every write in Dexie; flush automatically on app open/foreground and automatically on the browser's `online` event, plus an explicit "Sync now" button as a user-facing fallback/confirmation. This is the **entire** sync mechanism — one identical code path on both platforms, no feature detection. The Background Sync API (Chromium-only, unsupported on iOS Safari) is **deliberately not implemented** in v1: since the app can never depend on it for iOS anyway, and the triggered-sync design already covers essentially every real scenario, it would only add a second code path and testing surface for a benefit nobody would notice. It remains a valid future enhancement if ever needed — the Dexie queue design doesn't need to change to support it later.

- **Auth flow:** JWT access token (HS256, via PyJWT — FastAPI's own docs moved away from `python-jose` in 2024 after it went unmaintained). Single 30-day token, no refresh-token rotation for v1 — simpler to build and reason about while the author is new to JS, revisit if this is ever exposed beyond 2 users. Stored in the frontend's `localStorage`, sent as a Bearer header. `POST /auth/login` issues it; `GET /auth/me` is the first protected route, verified via a `get_current_athlete` FastAPI dependency.

## 3. MVP Scope

### Decided
- Auth: register/login/logout, secure password hashing (argon2-cffi), JWT-based token auth (see §2). Backend + frontend auth screens built 2026-08-31. **Mesocycle overview (Home) and workout logging (Workout) screens built and verified end-to-end 2026-09-14** — see decisions log; the 2026-09-02 entry claiming this was already done turned out to be inaccurate (no Workout screen existed, and Home was still the 2026-08-31 auth-stub) and is corrected there rather than deleted.
- Exercise library: name, description, equipment, movement category, exercise type (including "warmup" as its own type), granular muscles with a numeric contribution weight (not primary/secondary categories — see decisions log), supported set types, supported tempos, notes. Rep range is deliberately **not** a field on Exercise — it's a property of how an exercise is prescribed in a specific mesocycle, not of the exercise itself; it will live on the future Set Prescription entity.
- Program management: an athlete creates a mesocycle directly (no separate Program layer — see decisions log) with a length of 4-12 weeks (last week is always deload, derived automatically — never caller-specified per week), a deload strategy (rest / reduced load / none, reference-table-backed for future growth), and a fixed weekly split (reusable workout templates + exercise slots) that stays constant for the whole mesocycle. Creating a mesocycle produces a **draft** — an athlete can hold any number of drafts at once (e.g. planning the next block while training the current one); only *starting* one enforces one-ACTIVE-per-athlete. Stopping an active one lets the athlete choose (each time) whether to keep it as abandoned history or delete it outright. Mesocycles can be copied (duplicates the shape — weeks, templates, exercise slots — not prescriptions) into a new draft. Completed/abandoned mesocycles are locked against all add/edit/remove operations to preserve accurate history; editing a specific week's plan is also locked once a session has actually been completed against that week. "Current week" is derived from a running `sessions_completed` counter divided by training days per week — deliberately NOT calendar-based, so a missed/made-up training day shifts later sessions without creating a gap. Per-week numeric prescriptions (rep range, set type, tempo per set) are added per (exercise slot, week) pair; target RPE is not entered — it's auto-computed per week (see decisions log). Built and tested end-to-end 2026-08-29.
- Workout execution: start workout, see prescribed sets, log actual weight/reps/RPE (plus an optional free-text note) — deliberately NOT logging actual set type/tempo per set, since that felt like unnecessary friction mid-workout (see decisions log). Rest timer (target vs. actual) not yet built — that's a frontend/UI concern, not a backend data question. **Core loop built and tested end-to-end 2026-08-30.**
- History: previous workouts, previous exercise performance, weight/rep/RPE progression, volume, PRs.
- Basic progression: rule-based, deterministic, explainable next-week weight recommendation, auto-generated when a session completes based on reps achieved (vs. rep range) and RPE (vs. target — up to 1 point over allowed for an increase, 2+ points over on every set triggers a decrease). Weight steps to the next realistically loadable amount for the exercise's equipment (barbell/machine: 5kg, cable: 2.5kg, dumbbell: 1kg below 10kg then 2.5kg), never a raw percentage. Warm-up sets within a prescription are excluded from the decision and carried forward unchanged. **Built and tested end-to-end 2026-08-30, refined 2026-08-31** — see decisions log for the exact rule table.
- Offline support: complete a full workout with no connectivity, store locally (Dexie/IndexedDB), sync when connectivity returns (see §2 sync strategy).
- UI: mobile-first, dark, large controls, minimal typing.
- Set types supported from the start: warmup, straight, super, circuit, drop, pyramid, myo-rep set — modeled as their own reference table so new types don't require a redesign; tempo (normal/slow/explosive/paused) is a separate, independent dimension from set type.

- **2026-09-14** — Fixed the `stop_mesocycle(keep_as_history=False)` / `delete_mesocycle` 500 flagged in the entry below. Root cause: both do a plain `db.delete(mesocycle)`, which only cascades through relationships the ORM actually has declared (weeks, workout_templates and their direct children) — `exercise_prescriptions` (referenced from both weeks and template_exercises) and `workout_sessions` (referenced from mesocycles, weeks, and workout_templates) had no ORM relationship declared in that direction at all, so Postgres rejected the delete the instant a mesocycle had any prescriptions or sessions. Fixed at the database level rather than by adding more ORM relationships: added `ON DELETE CASCADE` to every FK in the planning/performed trees that was missing an action, and `ON DELETE SET NULL` specifically on `performed_exercises.template_exercise_id` and `set_performances.set_prescription_id` — both already nullable, both already meaning "no plan slot behind this" for freeform additions, so a later edit removing that plan slot should null the reference rather than destroy historical performance data. DB-level cascade was the right call over more ORM relationships because `workout_sessions` alone is reachable from three different parents (mesocycle, week, workout_template) that can each be hit first within the same delete — Postgres's constraint graph handles that correctly regardless of order; hand-rolled ORM cascade would have to get that order right itself. Confirmed the fix live against the actual dev Postgres database (not just the test suite): reproduced the original crash, then the same scenario plus an in-progress session with a logged set (exercising the `SET NULL` paths), both now succeed with no orphaned rows left behind. Also found and fixed a second, previously-undiscovered instance of the identical bug class: `remove_template_exercise` crashed the same way if a prescription existed on that slot — same migration fixes it, verified live too. Added a regression test (`test_stop_without_keeping_history_deletes_it_with_prescriptions_and_a_session`) — which required turning on SQLite's `PRAGMA foreign_keys=ON` for that test file's connection, since SQLite ignores FK constraints (cascade included) by default and the existing test suite had been silently exercising this code path with FK enforcement effectively off; confirmed the test genuinely catches the regression by reverting one `ondelete` and watching it fail with the same `FOREIGN KEY constraint failed` error before restoring the fix.

- **2026-08-30** — Built the v1 progression engine: a pure, unit-tested `decide_progression()` function (per constitution's "recommend_next_set" testability requirement) that auto-generates next week's weight recommendation the instant a session completes. Rule table, all per author's answers: missed the bottom of the rep range -> decrease 5%; hit the top of the range at or below target RPE -> increase 5%; RPE ran >0.5 over target even with reps in range -> decrease 5%; otherwise hold. Weight rounds to the nearest 2.5. A separate fixed rule handles the transition into a `reduced_load` deload week (flat 50% cut, per the author's own definition of that strategy, overriding the normal rule table); a `rest` deload week gets no recommendation generated at all, since nothing is trained. Recommendations are skipped (not guessed) where there's no sound basis: no performance data logged, an exercise swap occurred, or a prescription already exists for that slot+week. This surfaced a real, separate bug: `PrescribedSetResponse` never exposed the prescription's own id, so there was no way for a caller to link a logged set back to its plan at all — fixed alongside this milestone since progression's tests couldn't work without it.
